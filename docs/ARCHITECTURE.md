# 設計書：天使と悪魔（ガイスター互換ルール）

## 目的と制約

- スマホのブラウザで遊べる、指定した相手との1対1オンライン対戦
- ルールはガイスターと同一。見た目だけが異なる：
  - 自分の良いおばけ → 天使😇、自分の悪いおばけ → 悪魔😈
  - 相手のおばけ → すべて妖精🧚（種類は見えない）
- セキュリティを最大限配慮する
- 運用費は限りなく0円に近づける（目標：確実に月100円以下 → 設計上0円）

## アーキテクチャ（サーバーレスP2P）

```
[スマホA] ── 静的ファイル取得 ──> GitHub Pages (HTTPS)
[スマホB] ── 静的ファイル取得 ──> GitHub Pages (HTTPS)
[スマホA] <══ WebRTC DataChannel (DTLS暗号化) ══> [スマホB]
     │                                                    │
     └── 接続仲介のみ ──> PeerServer Cloud（無料枠）<── 接続仲介のみ ──┘
                          + Google Public STUN（無料）+ Open Relay TURN（無料・直接接続できない場合のみ暗号化データを中継）
```

| 構成要素 | 役割 | 費用 |
|---|---|---|
| GitHub Pages | HTML/CSS/JS の静的配信（公開リポジトリで無料、月100GBまでソフト制限） | ¥0 |
| GitHub リポジトリ | ソースコード管理（公開）。GitHub Pages はブランチ配信（ビルド不要の静的サイトのため） | ¥0 |
| PeerServer Cloud | WebRTC のシグナリング（接続仲介）のみ。ゲームデータは経由しない。同時接続50まで無料枠 | ¥0 |
| WebRTC P2P | 対戦データの直接通信。DTLS で暗号化 | ¥0 |
| Google Public STUN | NAT 越え支援 | ¥0 |
| Open Relay Project TURN | 対称型NAT同士など直接接続できない場合に、暗号化済みデータを中継する（中身は読めず保存もされない）。公開デモ用サーバーのためベストエフォート | ¥0 |
| **合計** | | **¥0/月** |

サーバーを持たないため、課金が発生する経路自体が存在しない。これが「月100円以下に確実に納める」ための最も強い保証になる。

### 代替案を採用しなかった理由

- **Firebase / Supabase 等の BaaS**：無料枠はあるが、プロジェクト作成や認証情報の管理が必要で、無料枠の条件変更リスクがある。本ゲームは隠れ情報の検証を暗号コミットメントで端末間完結できるため不要。
- **自前サーバー（VPS等）**：安くても月数百円〜で制約（100円以下）を満たせない。
- **TURN リレー常設**：対称型NAT環境では P2P が繋がらない場合があるが、TURN の帯域課金は予算と相性が悪い。対象は「指定した相手」との対戦であり、繋がらない場合は Wi-Fi 変更や再接続で回避する運用とする（既知の制約として明記）。

## 隠れ情報と不正対策（コミットメント方式）

ガイスター系ゲームの核心は「相手の駒の種類が見えない」ことと「後出しで種類をごまかせない」こと。

1. **配置時**：各端末は自駒8体それぞれに 128bit のランダムな nonce を生成し、
   `SHA-256("駒ID|種類|nonce")` のハッシュ一覧（コミットメント）だけを相手へ送る。
   ハッシュから種類は逆算できない（nonce が十分大きいため総当たりも不可能）。
2. **捕獲時**：取られた側がその駒の「種類＋nonce」を開示し、取った側がハッシュと照合する。
   一致しなければ不正として対戦を中止できる。
3. **脱出時**：脱出する側が天使であることを同じ開示方式で証明する。
4. **終局時**：両者が全駒を開示し、全コミットメントとの一致と、捕獲済み駒の種類の整合を検証して結果を表示する。
5. **移動の検証**：受信した手は全て、公開状態に対するルール検証（手番・所有・移動範囲・脱出マス）を通してから適用する。改変クライアントからの不正な手は弾かれる。
6. **入力検証**：受信メッセージは型・範囲・形式（ハッシュ長等）を検証し、不正メッセージが続く接続は切断する。サイズ上限も設ける。

残存リスク（受容するもの）：

- 対戦相手が「開示を送らず放置する」ことは防げない（知人同士の対戦前提。15秒で警告表示）。
- 改変クライアントが自分の駒の位置情報を通常より多く見ることは原理的に可能だが、公開情報しか存在しないため優位にはならない。相手の種類は相手端末にしか存在せず、ネットワークから盗むことはできない。
- PeerServer Cloud は無料のベストエフォート提供で SLA はない。停止時は対戦の新規接続ができない（代替として自前 PeerServer への切替を将来課題とする）。
- ホストの待機は sessionStorage に部屋コードを保持し、タブの再読み込み・破棄から戻っても同じ部屋で自動復旧する。対戦中の回線断は ICE 状態を見て猶予（6秒）以内に回復すれば切断扱いにしない。

## 接続とプライバシー

- 部屋コードは暗号論的乱数 16 文字（約79bit）。ホストは先着1接続のみ受け付け、2人目以降は切断する。
- 対戦データはサーバーに一切保存されない。アカウント登録、Cookie、アクセス解析はなし。
- PeerJS ライブラリは CDN から読み込まずリポジトリに同梱し、SHA-256 を `vendor/README.md` に記録（供給網対策）。

## ルール実装メモ

- 盤 6×6、自陣は各プレイヤーの手前2段の中央4列（8マス）、駒は天使4・悪魔4
- 移動は上下左右1マス、自駒のマス不可、相手駒のマスへは捕獲
- 勝利条件：(1) 相手の天使4体を捕獲 (2) 自分の悪魔4体を相手に捕獲させる (3) 自分の天使を相手側の角の脱出マスから脱出させる
- 敗北条件：相手の悪魔4体を捕獲してしまった場合（= 上記 (2) の裏返し）
- 先手はホスト（A）。再戦では先手を交代する
